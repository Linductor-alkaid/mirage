# DEC-013：前端信息架构（Harness 优先）与统一设计规范

> 状态：Accepted
> 日期：2026-09-16
> 负责人：Mirage 维护者
> 冻结里程碑：信息架构与风格规范自本记录起冻结（M1.5 落地骨架，M5 产品化验收基线）；
> 组件框架与工具链定案仍属 DEC-006 决策 6（M5）
> 替代/被替代：**修订**设计文档第 13 节"Agent Workspace 组织（而非围绕聊天历史）"
> 的口径——组织方式改为 harness 优先的统一壳（本记录决策 1），第 13 节其余内容

## 背景与问题

M1.5-04 交付了 Workspace / Tasks / Execution 三个视图（DEC-006 技术路线下的最小
闭环），但产品级信息架构未定：设计文档第 13 节早前倾向"Agent Workspace 而非聊天
历史"的组织方式，未回答——产品第一眼是什么、会话如何管理、设置有哪些类别、
workflow 编辑器选什么形态。维护者于 2026-09-16 明确产品方向：**Mirage 首先是
agent harness，其次才是 workflow，二者同级**；前端必须包含会话（chat）页、会话
历史管理与完整设置（常规/外观/模型/记忆/Skill/MCP 等），并要求先调研现有 agent
harness（opencode / pi / deepseek 等）与 RPA 开源前端，再融合定案。

## 决策

依据[前端调研](../research/2026-09-16-agent-harness-rpa-frontend-survey.md)与
pinned mira 契约盘点，冻结如下（规范全文见
[《Mirage 前端设计规范与信息架构》](../design/Mirage%20%E5%89%8D%E7%AB%AF%E8%AE%BE%E8%AE%A1%E8%A7%84%E8%8C%83%E4%B8%8E%E4%BF%A1%E6%81%AF%E6%9E%B6%E6%9E%84.md)，
下称《规范》）：

1. **信息架构 = harness 优先的统一壳**：活动栏一级导航为 会话（默认落地页）/
   工作流 / 资源（M2+ 占位）/ 设置；状态栏常驻主机态、运行摘要、默认模型与
   **紧急停止**。会话页 = 会话侧栏（历史管理：分组/搜索/重命名/置顶/fork/删除/
   导出）+ 消息流（工具调用默认折叠的活动卡 + 打断式批准卡 + 长会话轮次导航）+
   输入区（对话/执行双模式）+ 运行抽屉。M1.5-04 的 Workspace/Tasks/Execution 视图
   迁入该结构（映射见《规范》3.3），不废弃其能力。
2. **Workflow 编辑器为结构化步骤序列，不采用自由节点画布**：与 pinned mira
   `Workflow IR` v1 的"有序步骤 + 前置条件跳过 + Control 受限回跳"一一对应
   （自由图/子 workflow 是 IR 未承诺的扩展位，UI 不提前暴露）。步骤详情以桌面
   观察快照为第一载荷（快照 + 元素高亮 + 引用树/属性/JSON 三视图同步）；提供
   草稿/发布分离（agent 修改落草稿、发布需确认）与步骤级"让 agent 修复"。
3. **设置冻结为八类**：常规 / 外观 / 模型 / 记忆 / 技能 / MCP / 权限 / 运行时；
   其中模型、记忆、权限分别映射 mira `ModelProfile`、`MemoryScope` 与 DEC-010
   权限模型，MCP/Skill 面向扩展插槽（不硬编码）。
4. **统一风格规范**：《规范》§2 的三层设计 token（primitive → semantic →
   component；语义层与 shadcn 变量命名兼容）、明暗双主题（跟随系统）、状态色
   封闭映射（复用 M1 冻结状态集）、排版/密度/动效/无障碍基线，适用于 M1.5 浏览器
   形态、M3 壳形态与 M5 产品化形态，不出现两套视觉语言。
5. **IPC 前瞻依赖登记**：会话管理、会话消息流、workflow 管理、模型/记忆设置均
   需要 protocol v1 附加扩展（`session.*` / 消息事件集 / `workflow.*` /
   profile 管理面）；在契约落地前，UI 一律以 transport 接口 + mock 先行
   （M1.5-04 模式），前瞻项作为 DEC-007/DEC-012 演进输入登记，不阻塞交互定型。
6. **多主题（2026-09-16 修订增补）**：产品支持多套风格化前端主题供用户选择。
   主题 = 同一语义 token 契约的完整值集（light/dark 双套成对），以 `data-theme`
   机制挂载；组件零感知、切换即时生效；M1.5-08 交付 5 套内置主题（晨蓝默认/
   冷杉/暖沙/抹茶/玄墨）并按对比度与语义封闭门槛验收；外挂主题包属 P5 插槽
   （M5+）。机制、schema、清单与验收门槛见《规范》§2.6。

## 备选方案

- **沿用 Agent Workspace（任务为中心）组织**：否决。任务视图是 agent 运行的投影
  而非协作入口；行业共性（Claude/Goose/DSH/opencode）与维护者方向一致——会话是
  默认入口，任务/运行是会话与工作流的下属视图。
- **Workflow 采用 n8n 式自由节点画布**：推迟。Mira Workflow IR v1 是有序序列语义，
  画布表达力（分支/并行/子图）超出 IR 承诺，会出现"UI 可画、IR 不可执行"的漂移；
  IR 扩展位落地后重新评估（届时的融合形态参考调研：默认线性布局 + 局部分支）。
- **设置并入单页长表单**：否决。八类分类已对齐 mira 契约边界（profile/memory/
  permission 独立演进），长表单无法承载 MCP/Skill 插槽。

## 影响与风险

- 设计文档第 13 节口径修订（本记录）；第 17 节 `ui/` 代码结构不变（目录仍按视图
  域组织，`ui/workspace` 等占位目录与《规范》页面的映射在实现时于 `ui/README.md`
  维护）。
- M1.5 计划增补 `M1.5-07`（统一壳与信息架构重构）、`M1.5-08`（token 与基础组件
  落地）；M1.5-04 已交付视图按《规范》3.3 迁移，不回退。
- 会话/工作流/设置的后端契约尚不存在（决策 5）：前端先行走 mock，真实数据接入
  依赖协议演进排期，存在"界面先行于能力"的展示性空窗，需在各页标注能力来源
  （mock / 真实）。
- token 双主题与封闭状态色映射对后续视觉迭代是约束：调整需走设计评审并同步
  《规范》§2，不允许组件内私定颜色。
- 多主题（决策 6）扩大视觉验收面：每套主题都要过《规范》§2.6 的五项门槛
  （全量覆盖/对比度/语义封闭/证据可见/零位移），并以测试锁定"全量覆盖"，
  防止主题半成品进入发布。

## 验证方式

- M1.5-07/08 完成时：统一壳（活动栏/状态栏/路由表）与 token 全量落地，M1.5-04
  视图在新 IA 下功能等价（浏览器验收截图对照《规范》3.3 映射）；预设矩阵与前端
  测试不回归。
- 持续：新增页面/组件必须引用《规范》token 与组件规格；偏离需修订本记录或
  《规范》并留变更记录。
- 主题（决策 6）：新增主题 PR 必须附 §2.6 五项门槛的核对证据（覆盖测试 +
  对比度计算 + 截图）；《规范》§2.6 是唯一准入标准。
- M5 产品化验收以《规范》为基线（含设置八类、workflow 编辑器 IR 对齐、批准中心）。
