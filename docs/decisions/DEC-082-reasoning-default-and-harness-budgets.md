# DEC-082：MiniMax 默认思考通道与桌面任务预算

- 状态：Accepted
- 日期：2026-10-12
- 工作项：M6-26 / M6-38、M7-07 / M7-10
- 负责人：Mirage 维护者

最新会话中，两次默认档的服务端 reply_text 是作答计划，没有 ThinkingPart；另一轮
开启思考的桌面任务在第 7 次模型调用后以 MaxTurns 失败，尚未进入文字输入与发送。
前者不是 UI 将结构化思考误作正文；后者来自宿主 65536 整环预算 / 8192 每轮预算，
按 pinned ConversationLoop 的额外一次请求信封算出 7 轮。此前两次点击已成功，不能
将本次故障归为 Wayland 输入不可用。

MiniMax 官方 Messages 文档说明 M3 未传 thinking 默认关闭，Adaptive 开启独立思考；
max_tokens 同时覆盖思考和正文。无历史的线上合成探针三档均能正常作答，尚未稳定
重现默认档错误，不能宣称所有默认请求必然返回思考。参考：
[MiniMax Messages API](https://platform.minimax.io/docs/api-reference/text-anthropic-api)。

产品对精确型号 MiniMax-M3 的 Messages 默认档显式选择 Adaptive，与“开启”相同；
用户显式“关闭”仍发送 Disabled，其他型号默认继续由供应商决定。纯对话和 Agent
使用相同映射，正文只取 MessageOutput；非 redacted ThinkingPart 仍进入既有折叠过程。
两个系统提示明确要求用户可见正文直接作答，过程说明只在必要时使用。不得通过中文
关键词猜测或删除正文，也不在发现疑似思考后自动追加网络重试。

已知支持 Messages 思考的型号配置整环输出信封为
17 × max(已配置每请求上限, 8192)，支持最多 16 次模型调用、32 次工具执行，恢复次数
仍为 0。单次生成上限仍为关闭档配置值、开启档至少 8192，不将整环额度发成单次额度。
这复用 Mira 公开 ConversationLoop 的整环准入语义，不改 pinned 实现或另建 Agent 循环。
未知型号原路由预算不变。较长任务仍可能耗尽有限预算，必须显式失败而非冒充完成。

ModelLayerConfig 新增 harness_deadline，默认 10 分钟，范围 (0, 10 分钟]；纯对话与
单次模型调用继续使用 request_deadline（默认 2 分钟）。Runtime Service 根据已冻结的
agent 选择整体 deadline，既有 Executor StopToken、工具取消与关闭路径不变，不新建
线程、定时器、队列或生命周期。预算内允许多步任务推进，用户停止仍立即阻止新动作。

验收包括默认/关闭/开启参数与正文/思考分离、超过 7 轮仍完成、跨越单次请求时间但
未越过整项任务时间、16 轮终态、整体超时/取消/异常/拒绝/关闭，以及三模式菜单与
按钮的左对齐、向上展开和 4px 间隔。实际桌面授权和原用户任务闭环仍待维护者复验。

最新用户任务还要求向 Mirage 自己的会话发送文字。活动会话的按钮实际为停止，
Enter 拒绝新提交。宿主提示补充该产品事实：不要将停止误作发送，只在符合用户
目标时选择另一空闲会话；否则明确说明限制。保留现有 UI 忙门禁，不开放并发写入
同一活动会话，不宣称仅增加轮数即可保证该具体任务成功。
