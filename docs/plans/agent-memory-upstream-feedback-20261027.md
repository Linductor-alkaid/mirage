## 用户目标：始终面对同一个 Mira

用户只需要一个持续可用的输入口。无论是在聊天、提出新任务、补充要求、纠正先前的
指令、追问旧事，还是暂停/恢复工作，都直接对 Mira 说。**由 Mira 内部安排输入所属的
会话和任务，管理各自的上下文，选择读取与写入哪些记忆，再通过统一交互流回应用户。**

本条提出记忆系统、上下文管理、会话/任务管理和用户交互契约的完整需求。用户无需为了
让系统正确理解一句话而先新建会话、切换会话、选择运行模式或手动搬运上下文。
内部可以在有限预算内管理多个 Session、Task、Working Context 和记忆 scope；它们是 Mira 组织工作
的机制，用户可按需查看任务/历史，但日常输入不依赖这些内部标识。

Mirage 的[持续性数字个体路线图 v1.1](https://github.com/Linductor-alkaid/mirage/blob/83c60476f399103e8d7b3c451fa0fda631ee6c84/docs/design/continuous-digital-entity-evolution.md)
§4.2～4.5 已提出统一身份、内部任务协调、动态工作记忆和无需选择会话的交互。
2026-10-27 维护者进一步明确：**Mira 自己负责输入后的会话、上下文和记忆安排**。
本 issue 据此替换初版仅关注回忆反馈/激活排序的范围；编号仍为 `MIRA-20261027-001`。
路线图仍待修订，具体类名、公式、数据库表和排期不作为已冻结方案。

## 期望的完整闭环

```text
用户持续输入
  → 统一接纳、关联身份和输入编号
  → Mira 理解意图，决定延续/创建/恢复/暂停/纠正哪个任务或内部会话
  → 准备该任务的 Working Context、近期交互与相关历史/长期记忆
  → 经现有 Runtime / Loop / Tool 执行并验证
  → 更新任务状态、上下文投影和可沉淀的记忆候选
  → 在同一用户交互流返回答复、进度、澄清或需要用户处理的事项
```

一次任务结束或一次模型回答结束后，这个面向用户的交互关系继续存在。
上下文压缩、内部会话切换、模型请求窗口变化和进程重启不要求用户重新介绍自己或
手工复述已保留且有权限访问的任务状态。

## 需要交付的行为与契约

### 1. 统一输入接纳与输出关联

- 提供高层宿主集成入口：输入至少能关联已认证的主体、稳定 input id、内容和必要的
  回复/附件引用；普通输入不要求调用方先给出 SessionId。具体 API 名称与类型由上游设计。
- 明确接纳、理解/路由、执行、回答和任务完成的不同阶段；收到输入不等于任务已完成。
- 在声明的有限重试/去重窗口内，相同 input id 的重试不得重复建任务或派发副作用；
  窗口外的旧请求必须有明确拒绝/过期语义，不能清掉台账后将其当成新动作。不同输入即使内容相同也不能
  自动当成重试。并发到达、连接重试、背压与关闭中的输入均有明确结算。
- 所有回复、追问、后台结果和失败可追溯到原始输入及相关任务；支持断线后的有界回补。
  统一交互流能说明“Mira 正在做什么、哪些还未完成、现在需要用户补充什么”。

### 2. Mira 内部管理会话与任务

- 对输入作出可审计的安排：普通交流、延续当前工作、补充/纠正某项工作、新建任务、
  恢复旧任务、取消或暂停工作。一个输入可能关联多个工作项，需要保留拆分关系。
- 关联依据包括当前交互、活动/挂起任务、用户显式引用和授权范围内的历史；不把
  “最近一个 Session”当成所有输入的唯一默认归属。
- 指代不清或多个候选都合理时，在同一入口进行自然语言澄清，不要求用户理解内部
  SessionId。明确的补充也不应每次都触发多余澄清。
- 长任务执行中仍能接收新输入。新话题和旧任务可分别推进；任务的优先级、等待和
  前后台关系由 Mira 的通用协调策略管理，平台资源能否并发由宿主能力与租约反馈决定。
- 模型可提出路由/切换建议，确定性 Runtime 验证状态与权限后提交；不因一句自然语言
  推断而静默重写历史或复活已终态任务。路由纠正须明确处理先前结果及在途动作。
- 暂停、恢复、接管、紧急停止复用已有控制面；紧急停止应有直接的确定性控制路径，
  不依赖下一次模型路由成功。

### 3. 自动管理每项工作的上下文

- 每次模型请求按当前工作组织：目标、最新用户约束、任务状态、未决副作用、近期热
  上下文、已提交 Working Context、需要召回的历史与记忆。
- 插话纠正应更新正确任务的后续上下文；不相关话题不污染其他任务的状态或约束。
  全局偏好、当前指令与任务局部要求的生效范围应明确，不能靠拼接所有会话历史处理。
- 根据预算做裁剪、压缩、检索和按需回溯，按有效保留策略保留关键决定、失败原因与可用原始证据引用；
  内部换会话/恢复工作时仍能找回所需状态。
- 复用 Layer 0 对预算、authority、epoch 和最低执行集合的最终准入，维持工具
  call/result 配对；上下文不足或投影失败时明确降级/失败，不假装完整记得。

### 4. 长期记忆的写入、检索、纠正与遗忘

- 从交互和已验证结果提出长期偏好、事件经历、事实、经验等候选，沿已有 consolidation /
  promotion 管线校验和写入；按当前任务选择实际需要的记忆进入上下文。
- 区分原始事实记录、任务工作状态、可重建上下文投影与长期记忆；活动任务、承诺调度
  和未决副作用不能仅靠相似度召回维持。
- 用户纠正、“以后记住……”与“忘掉……”要能关联到正确记录/范围，经现有权限和
  policy 处理；冲突、来源、有效期和删除状态可解释。频繁提到一件事不等于它变得可信。
- 初版提出的可验证回忆反馈、importance/使用信号与查询相关性分离的排序属于本层
  可选增量。是否新增 API、分几步做由上游评审，不应先冻结激活公式而遗漏完整交互闭环。
- 跨会话召回继续服从精确 scope/tenant ACL；同一个用户入口不取消任务隔离、授权和
  隐私删除约束，记忆中的授权描述不能代替当前有效授权。

### 5. 面向用户的持续交互与可恢复状态

- 输入口在执行任务、等待工具或等待某个澄清时持续可用；新输入的接纳有界且可观察。
  用户可以继续交流、查询进展、纠正和取消，无需跳到另一个内部会话。
- 在统一反馈中区分“已收到”“正在处理”“等待某条件”“已回答”“任务完成/失败”；
  背景任务的迟到消息保留归属，避免看起来像是在回答用户刚发出的另一句话。
- 重启恢复已接纳输入的处理状态、内部任务/会话映射和必要上下文；未决副作用必须
  先重观测/验证，不能因恢复流程重复执行。历史缺失、已擦除或不可恢复时明确说明。
- UI 可以提供任务列表、进展、历史详情与用户纠正入口；创建/选择会话不再是日常交流
  的前置步骤。具体页面与控件由 Mirage 实现，所需状态/事件/交互语义应由 Mira 提供。

### 6. 有限容量、主动遗忘与会话归档清理（部署必需）

持续交互不承诺无限记忆或永久保存全部原始经历。实际部署必须对记忆和内部会话
形成资源上界，零星旧事件允许被选择性遗忘。**遗忘不能只等于降低召回分数，归档
也不能变成另一个无限增长的数据池。** 具体机制必须先设计评审、测试，再用于真实数据。

**预算范围与接纳**

- 规定有限的记忆条目/字节、受管理/驻留会话数、归档数量/字节/保留期；原始事件、
  Working Context/checkpoint、附件/截图、向量索引、历史版本、墓碑、幂等台账和受管
  备份也计入预算。并行任务/输入、单对象大小和进程内缓存亦有上限。
- 区分总预算、分主体份额、软水位、硬水位与回收/取消所需预留；计入摘要生成、索引
  重建、数据库/WAL/临时文件的峰值。具体数值由部署档位和目标设备验证冻结。
- 容量预留与并发接纳一致；软水位下主动巩固/回收，硬水位下有界背压/拒绝。
  回收失败、磁盘满或全部为受保护数据时应报告阻塞原因，不能默认扩大容量或静默丢数据。
  仅有单次清扫上限或请求 token 上限不能证明持久化总量有界。

**分层遗忘与信息价值**

- 区分召回降权、去重/抽象巩固、有限归档和物理删除，明确各层的触发/退出条件。
  候选策略综合经验证的重要性、时效、实际用途、冗余、可重获性、敏感性和保存成本；
  不把纯 LRU、年龄或未经验证的模型评分作为全部规则，不在本 issue 冻结公式。
- 采用“先验证并可靠提交摘要，再清理旧内容”的失败安全步骤；摘要保持来源/有效性，
  防止歪曲事实、自我强化与层层摘要无限积累。原文被清理后明确不可回查，不能伪造证据。
- 活动/挂起任务的最低必要状态、未决副作用、待批准/待澄清事项及当前安全/授权约束
  不按普通情景记忆淘汰；它们同样需要预留和接纳上限。保护集合已满时限制新工作，
  不能无限增加保护项。用户固定的重要记忆也需要有限配额，而非无限期容量豁免。
- 普通旧事件和已无用途的细节可以到期/按压力物理删除。重要事实优先保留，不承诺
  永远记得所有事件；用户查询已清理内容时说明限制，必要时重新获取，而非补造经历。

**会话退出与有限归档**

- 定义内部协调生命周期：受管理/可执行 → 收敛中 → 可归档 → 已归档 → 已清理。
  这是待设计的高层状态，不直接修改已有 SessionState。
- 完全完成且不再使用的会话自动进入归档流程：所有关联任务终态，无在途工具、待处理
  输入/结果、待确认/澄清、未决副作用、租约及未结算的上下文/记忆更新；必要结果已
  可靠记录，并满足明确的交付/过期策略。清理前重查版本和存活引用，处理新输入重新
  关联旧会话的竞态。单个 Task Completed 或“空闲很久”都不等于可直接删除。
- 归档释放受管理/驻留会话名额，保留有限摘要/元数据和必要工件；归档有自己的总额和
  保留期，超限/到期后可清理。后台结果长时间无人读取也须有有限、明确的交付过期规则。
- 恢复/查询归档按需且占用接纳预算，不启动时全量驻留。终态任务不复活；后续工作可
  关联旧摘要新建任务。已清理原文不能假装可恢复；同一入口仍可解释目前保留的内容。

**跨存储一致性与可证明回收**

- 复用现有 TTL/retention/erase、checkpoint 和 ArtifactStore 能力；新增的是总容量准入、
  价值/压力驱动的遗忘与跨会话归档协调。容量回收失败和用户隐私删除分别结算，
  不能借回收解除 Erasure Pending 的 hold，也不能把归档当成“忘掉了”。
- 删除前检查共享工件/记忆的所有权和存活引用；清理一个会话不得删掉其他工作仍需的
  证据。摘要/索引/引用/受管备份的生命周期一起考虑，隐私删除后不能从它们重建正文。
- 跨 store 清理要幂等、可取消/恢复，覆盖中途崩溃、迟到写入和迁移；删除记录、摘要、
  墓碑与回收日志本身也有上界，定义过期引用与旧输入重放行为，防止删除后复活。
- 分别报告逻辑删除、可重用空间与实际文件占用/峰值，证明长期写入下真实资源收敛；
  不能仅以“删掉若干行”证明磁盘预算达标。所有工作沿用 kairo 的受监督生命周期。

**与既有决策的冲突**

Mirage DEC-101 曾默认 `max_sessions=0`，路线图曾规定“遗忘只是激活降低、原始记录
仍可检索”。维护者本轮明确以有限容量取代这两个前提，已记录为 Mirage DEC-119。
当前实现尚未迁移、未执行数据清理。Mira 现有 TTL/erase 与有界 sweep 是复用基础，
不是新诉求已经实现的证明；涉及上游 Raw Trace/可重建性约定也须按保留窗口重新审视，
不宣称被删除的源数据仍能无限回放。具体算法、预算、API 与迁移设计由上游后续冻结。

## Mira 与 Mirage 的职责

**Mira 承担通用协调**：主体级交互生命周期、意图与会话/任务安排、上下文与记忆编排、
恢复及结果关联。实现位置可为现有 Runtime 之上的高层 coordinator，具体边界由设计
评审冻结；沿用现有 Runtime/Loop/Memory 组件，避免另建一套控制面。

**Mirage 承担产品与平台**：统一输入/输出 UI、IPC、身份认证和授权配置、桌面资源租约、
环境观察与动作执行、进程/存储/模型供给。宿主向 Mira 提供这些能力和事实；每个 Host
无需重新实现一整套会话路由、上下文与记忆决策。产品时间线是 Mira 交互状态的投影，
具体存储接线与 UI 不要求进入 Core。

所有异步、定时、I/O、取消和关闭继续由 Mira 交付的 kairo 管理，owner 明确，
结果经现有 future/诊断/事件可观察；不新增私有线程池、队列或平行生命周期。
旧的显式 session/task API 可保留给高级集成与调试，高层入口负责默认用户交互。

## 验收场景

全程使用同一个输入口，不手动创建/选择会话：

1. **连续交流**：“帮我整理季度报告”→“用中文，重点写风险”。第二句进入正确任务，
   更新后续约束；用户无需再次提供报告上下文。
2. **穿插话题**：整理报告时“先帮我查一下这个术语”→“继续刚才的报告”。普通交流与
   报告状态分别保留，后续能回到报告，不把临时话题覆盖成任务目标。
3. **并行工作与指代**：两个任务未完成时，输入明确引用可路由；“把那个停下”无法确定
   目标时从同一入口澄清。已明确的紧急停止走确定性控制路径。
4. **插话纠正/取消**：执行中修改范围或取消，更新目标任务；在途动作安全收敛，迟到的
   结果不复活旧任务，也不覆盖新的要求。接纳纠正不宣称已撤回发生过的副作用。
5. **跨时记忆**：“以后报告默认用中文”后新建另一项报告工作，可在授权范围内使用
   已认可偏好；用户随后纠正/删除该偏好，旧投影与后续召回遵守更新/删除语义。
6. **压缩和重启**：长交互触发压缩或重启后“继续刚才的报告”，恢复正确任务和证据；
   缺失资料明确说明，未决副作用不盲目重放。
7. **并发/重试/隔离**：重复 input id 不产生第二项副作用；多个输入与后台结果保持归属；
   不跨 principal/tenant/scope 泄漏内容；预算、背压、失败和 shutdown 结果明确。

8. **容量长期收敛**：用小配额持续写入不同大小的事件/附件/记忆，越过软/硬水位；
   验证驻留/受管理会话数、归档总量、实际文件占用与峰值始终符合冻结预算。保护集合满、
   磁盘满和回收失败可见、有界，不以无限归档或删除计数代替资源测量。
9. **安全归档/遗忘**：完全结束的会话释放管理名额并最终清理；仍有工具、未读结果、
   更新或共享证据引用时不能误删。覆盖查询归档、新输入重新引用、清理中崩溃/取消、
   原始证据过期、隐私删除后不复活，以及去重台账过期后旧请求不重复副作用。

先用脚本化语义供给验证接纳/路由提交、状态一致性、上下文归属和故障恢复，再用标注
场景与真实模型评估路由准确率、必要澄清率、上下文约束保留、记忆纠正生效、延迟与资源。
不能以“具备向量检索”或“单个 loop 跑通”代替这组端到端验收。
